# Extension AI Guard — Phase 14 Classical Machine Learning

## 1. Phase Overview

Phase 14 is the Classical Machine Learning phase of Extension AI Guard (EAG).

The purpose of this phase is to train, evaluate, and preserve multiple classical machine learning models using the processed and validated dataset produced by Phase 13.

The models will learn to classify network traffic behavior into:

- BENIGN = 0
- MALICIOUS = 1

Phase 14 does not replace the Phase 13 preprocessing pipeline. It consumes the frozen and verified Phase 13 artifacts.

The results produced in this phase will establish the classical machine learning baseline that will later be compared with the Quantum ML work in Phase 15 and the comparative evaluation in Phase 16.

---

## 2. Phase Objectives

The objectives of Phase 14 are:

1. Verify all required Phase 13 preprocessing artifacts.
2. Train multiple classical machine learning algorithms.
3. Maintain strict separation between training and testing data.
4. Use reproducible random seeds where supported.
5. Handle class imbalance appropriately where supported by the selected estimator.
6. Evaluate every model using the same isolated test dataset.
7. Measure classification performance using multiple metrics.
8. Benchmark model training and inference execution time.
9. Generate confusion matrices and structured evaluation results.
10. Save trained model artifacts for later phases.
11. Generate a unified baseline_metrics.json file.
12. Create automated validation tests.
13. Document the complete methodology and results.
14. Prepare a reusable classical ML baseline for Phase 15 and Phase 16.

- time_relative
- frame_len

### Categorical features

## 5. Data Leakage Protection

Data leakage prevention is a mandatory requirement.

The Phase 13 preprocessing pipeline was fitted using training data only.

Phase 14 will use the already processed training and testing artifacts.

Models must be fitted exclusively on:

X_train
y_train

Models must be evaluated exclusively on:

X_test
y_test

The test labels must not influence model training, hyperparameter selection, threshold selection, or model configuration.

No test-set information may be used to improve a model before the final evaluation.

## 6. Classical ML Models

Phase 14 will establish a diverse classical ML baseline.

The planned models are:

### 6.1 Logistic Regression

Purpose:

Provide a linear classification baseline.

Characteristics:

- Simple
- Fast
- Interpretable
- Suitable baseline for binary classification

Class imbalance handling will be configured where supported.

---

### 6.2 Decision Tree

Purpose:

Provide a rule-based nonlinear classifier.

Characteristics:

- Captures nonlinear decision boundaries
- Easy to inspect
- Provides interpretable decision rules

Tree complexity will be controlled to reduce unnecessary overfitting.

---

### 6.3 Random Forest

Purpose:

Provide an ensemble tree-based baseline.

Characteristics:

- Combines multiple decision trees
- Captures nonlinear relationships
- Provides feature importance information
- Useful for cybersecurity classification experiments

A fixed random state will be used for reproducibility.

---

### 6.4 Support Vector Machine

Purpose:

Provide a boundary-based classifier.

Characteristics:

- Effective for structured feature spaces
- Can model nonlinear separation through kernels
- Useful for comparison with linear and tree-based methods

Probability estimation will be enabled only when required for ROC-AUC/probability-based analysis because it can add computational overhead.

---

### 6.5 K-Nearest Neighbors

Purpose:

Provide an instance-based classification baseline.

Characteristics:

- Makes predictions based on neighboring training observations
- Requires no learned parametric decision function
- Provides a different learning approach from tree and linear models

KNN does not use class_weight in the same way as the selected weighted classifiers, so class imbalance handling will be evaluated separately rather than forcing an unsupported configuration.

---

### 6.6 Gradient Boosting

Purpose:

Provide a sequential ensemble baseline.

Characteristics:

- Builds models sequentially
- Attempts to correct previous prediction errors
- Provides another nonlinear ensemble approach

Randomness will be controlled where supported.

## 8. Class Imbalance

The dataset contains:

BENIGN: 112

MALICIOUS: 32

Therefore, the dataset is imbalanced.

Where supported by an estimator, class weighting may be used to reduce the tendency to favor the majority class.

The implementation will not blindly apply class_weight='balanced' to every algorithm.

Only compatible estimators will receive class weighting.

Models without an equivalent class-weight mechanism will be documented and evaluated using the same test data.

The goal is to reduce missed malicious samples without artificially duplicating the dataset.

---

## 9. Evaluation Metrics

Every applicable model will be evaluated using:

### Accuracy

Measures the proportion of all test samples classified correctly.

### Precision

Measures how many samples predicted as MALICIOUS were actually MALICIOUS.

### Recall

Measures how many actual MALICIOUS samples were detected.

Recall is particularly important because false negatives represent malicious traffic incorrectly classified as BENIGN.

### F1-score

Provides a balance between precision and recall.

### ROC-AUC

Measures the model's ability to distinguish the two classes across decision thresholds when probability or decision scores are available.

### Confusion Matrix

The confusion matrix will explicitly record:

- True Negatives
- False Positives
- False Negatives
- True Positives

The number of false negatives will be recorded separately.

---

## 10. Performance Benchmarking

Phase 14 will record execution performance in addition to classification metrics.

For every model, the following will be measured:

- Training time in seconds
- Total inference time in seconds
- Inference time per test sample in milliseconds

Training time will be measured around:

model.fit(X_train, y_train)

Inference timing will be measured around prediction on X_test.

Inference time per sample will be calculated from total inference time divided by the number of test samples.

Timing measurements will be treated as experimental observations rather than universal hardware-independent performance claims.

## 15. Model Comparison Principle

Phase 14 will not select a model based on accuracy alone.

The results will be compared across:

- Accuracy
- Precision
- Recall
- F1-score
- ROC-AUC
- False positives
- False negatives
- Training time
- Inference time
- Inference time per sample

No model performance values will be assumed before actual execution.

---

## 16. Overfitting Controls

The dataset is relatively small.

Therefore, Phase 14 will avoid unnecessarily complex models and excessive tuning against the test set.

Controls include:

- Fixed train/test split
- Test-set isolation
- Reproducible random state
- Controlled tree complexity
- Limited model configuration
- No test-set-driven hyperparameter tuning
- Multiple evaluation metrics
- Confusion matrix inspection

The purpose of Phase 14 is to establish a reproducible baseline rather than optimize the model specifically for the current test set.

---

## 17. Dataset Limitations

The Phase 12 dataset contains only 144 packet-level samples:

- 112 BENIGN
- 32 MALICIOUS

The dataset was generated from a controlled laboratory environment.

Therefore, Phase 14 results must not be interpreted as proof of production-grade detection accuracy across all browser extensions.

The final EAG system is intended to generalize beyond the controlled extension samples.

Additional data diversity and later evaluation phases are therefore important.

---

## 18. Generalization Requirement

A central EAG requirement is that the eventual detection system must not simply memorize the controlled malicious extension or the laboratory environment.

Phase 14 therefore preserves the leakage protections established in Phase 13.

The following must remain excluded from the ML feature matrix:

- Lab-specific IP addresses
- Capture-specific frame numbers
- Controlled endpoint URI identifiers
- Capture-specific raw ports

The model should learn network behavior rather than laboratory identity.
